## Global Constraints

- Every workstream ends with `scripts/check.sh` passing locally before a PR — this is the project's gate; it runs `fmt --check` first, then clippy, then tests. Capture its exit code to a file, never through a pipe: `scripts/check.sh > /tmp/gate.log 2>&1; echo $? > /tmp/gate.exit`. Verify success by reading the log for `All checks passed`, zero `FAILED` lines, and `REAL_EXIT=0` — not by trusting a piped exit code.
- `CARGO_BUILD_JOBS=2` (the gate OOMs above ~6 parallel jobs on this machine).
- Ensure `~/.cargo/bin` is on `PATH` before running the gate, or `nextest` silently falls back to a ~90-minute serial run. Confirm the nextest banner appears.
- Use a per-branch `CARGO_TARGET_DIR` (e.g. `export CARGO_TARGET_DIR=/tmp/sbproxy-target-<branch-name>`) — a shared target dir across concurrent worktrees produces stale-rmeta false failures.
- Any change to a `#[derive(JsonSchema)]` struct requires running `scripts/check-config-schema.sh` (regenerates `schemas/sb-config.schema.json` and the `ai-proxy-provider` schema) — the local gate does not do this automatically.
- Run `cargo fmt` before every gate run — it's the gate's first check and the fastest to fail on.
- No em dashes in any committed prose (code comments, docs, commit messages, PR descriptions).
- No `Co-Authored-By: Claude` or similar AI-attribution lines in commit messages or PR descriptions.
- No Linear ticket IDs (`WOR-####`) in `docs/`, `CHANGELOG.md`, `README.md`, or PR descriptions — those are buyer-facing. (This plan document itself is an internal planning artifact, not shipped documentation, so it's exempt — but strip WOR-#### references from anything it produces that ships, per each task's instructions.)
- Never run destructive git operations (`push --force`, `reset --hard`, branch deletion) without explicit confirmation from whoever is running this plan.
- If a task's tests touch a struct literal that other crates also construct (e.g. `AdminOperator { ... }`), grep the whole workspace for that literal before considering the task done — a per-crate compile passing does not mean every construction site was updated.

```rust
/// Walks `raw_config`'s parsed JSON tree and returns every entry in
/// `INERT_CONFIG_KEYS` whose dotted path is present in the tree, meaning an
/// operator actually set it (not merely that the schema declares it).
pub fn set_inert_keys(raw_config: &serde_json::Value) -> Vec<&'static ConfigKeyCapability> {
    INERT_CONFIG_KEYS
        .iter()
        .filter(|capability| json_path_is_set(raw_config, capability.key))
        .collect()
}

fn json_path_is_set(value: &serde_json::Value, dotted_path: &str) -> bool {
    let mut current = value;
    for segment in dotted_path.split('.') {
        match current.get(segment) {
            Some(next) => current = next,
            None => return false,
        }
    }
    true
}
```

```markdown
# Admin operators: config or runtime state

Status: accepted. Operators stay config-defined; the admin console shows
them read-only; passwords are hashed at rest.

## Context

1. Config authority (WOR-2005) establishes that the config editor is
   read-only wherever config is not locally owned. A runtime-state users
   page would be editable on some fleet nodes and not others, for reasons
   an operator can't see from the UI.
2. Inbound API keys faced the identical fork and became mutable runtime
   records (KeyRecord) seeded from config, gaining hashing, rotation, and
   an audit trail for free. Operators could copy that shape, at the cost
   of a second record kind and a fleet config that no longer fully
   describes the fleet.
3. AdminOperator.password is plaintext in YAML today. Once WOR-2005 signs
   and distributes config to every node in a fleet, that plaintext ships
   to every node in cleartext.

## Decision

Operators stay config-only. No admin API, no CRUD, no runtime record.
The admin console adds a read-only view showing who can sign in, with
provenance (which config source declared them).

`AdminOperator.password: String` becomes `AdminOperator.password_hash:
String`, hashed with the same HMAC-SHA256-plus-pepper primitive
`sbproxy-keystore` already uses for inbound API keys
(`KeyCrypto::hash_secret`/`verify_secret`), not a new scheme. Login
checks become `verify_secret(supplied, pepper, stored_hash)` instead of
a plaintext comparison. The hash value can be supplied via the existing
`${VAR}` textual interpolation (works automatically, no new code) or the
`sbproxy-vault` secret-reference resolver (`vault://`, `secretfile://`,
etc., wired explicitly at the point AdminOperator config converts into
the runtime type) for operators who want it out of the YAML file
entirely.

## Consequences

- Rotating an operator's password still means editing config and
  reloading, same as today's "edit YAML" plaintext model, just now with
  a computed hash instead of a literal password. A small `sbproxy admin
  hash-password` CLI helper is worth adding so operators don't need to
  invoke the HMAC primitive by hand (out of scope for this decision; a
  follow-up ticket if this friction turns out to matter).
- The `/admin/config` read endpoint already returns raw config text
  verbatim, unredacted for this struct. A password_hash is
  low-sensitivity to expose (an HMAC hash isn't directly usable to log
  in), unlike the plaintext password it replaces, so this is an
  improvement even without adding new redaction.
- The bigger "should admin identity generally be runtime state" question
  (option A from WOR-2038) stays open. This decision resolves only the
  operator-password shape; it does not preclude revisiting runtime
  operators later if self-service rotation becomes a real requirement.
```
