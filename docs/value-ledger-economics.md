# Value Ledger Economics

*Last modified: 2026-08-16*

The SBproxy AI gateway includes a robust economic observability engine known as the **Value Ledger**. It provides concrete reporting on the exact monetary savings generated by running inference on local or self-hosted models ("Local Lane") versus spilling traffic over to a paid cloud provider ("Cloud Lane").

Because SBproxy can transparently route and failover between local models (e.g., Llama 3 via `sbproxy-model-host`) and cloud fallbacks (e.g., OpenAI, Anthropic), operators need to understand their exact ROI. The Value Ledger continuously tracks these savings and actual cloud spends.

## 1. Lane Splits

The ledger tracks a "local-vs-cloud split" for every finished completion whose served model has a configured cloud reference price. 

It reports four primary economic figures:
1. **Total Local Completions:** The number of requests successfully served by a local or self-hosted model.
2. **Total Cloud Completions:** The number of requests that were successfully served by a fallback cloud provider (e.g., because the local model was overloaded and the admission gate refused it, or it returned a retryable 5xx).
3. **Total Saved:** The gross monetary value saved (tracked in micro-dollars) by successfully answering requests locally instead of via the reference cloud provider.
4. **Total Cloud Spent:** The actual monetary amount spent (tracked in micro-dollars) when a request displaced to a cloud provider.

## 2. Configuring Reference Prices

The Value Ledger does not guess prices. It requires explicitly configured reference prices on your `serve:` or local model definitions. 

When configuring a local model, you specify the reference cloud model that it displaces and its price in micro-USD per 1,000,000 tokens (prompt and completion, tracked separately).

For example:
```yaml
origins:
  "ai.local":
    action:
      type: ai_proxy
      providers:
        - name: local
          serve:
            models:
              - model: qwen2.5-coder
                # Track how much we save compared to calling GPT-4o.
                # Prices are in micro-USD per million tokens.
                reference:
                  model: gpt-4o
                  prompt_micros_per_mtok: 5000000
                  completion_micros_per_mtok: 15000000
```

When a request for `qwen2.5-coder` is served by the local model host, the Value Ledger logs a **local lane** completion and credits the savings based on the `gpt-4o` token cost.

## 3. Spillover and Cloud Attribution

If the local model host is overwhelmed and the proxy's failover loop advances to a fallback cloud provider, the Value Ledger tracks this as a **cloud lane** event.

The ledger explicitly tracks what lane the request took using the `served_model` property. This prevents attribution bugs. For example:
- If a request for `qwen2.5-coder` spills over to a cloud fallback provider that isn't using a `model_map` (i.e. it passes through the model ID `qwen2.5-coder` verbatim), the Value Ledger knows this was answered by the cloud lane, not the local lane. It correctly records a cloud spend, rather than falsely crediting a local saving.
- The cloud spend is placed under the requested model's key so that reports accurately reflect "what this lane cost when the local box could not take it".
- If a request spills over to an unreferenced model (a model with no `reference:` block), nothing is recorded in the Value Ledger.

## 4. Querying the Ledger

The Value Ledger can be read two ways: through the Admin API on a running proxy, or with a CLI report against the ledger file itself.

On a running proxy, use the authenticated Admin API endpoint `GET /admin/model-host/value`:

```bash
curl -fsS -u "admin:${SB_ADMIN_PASSWORD}" \
  "${SB_ADMIN_URL}/admin/model-host/value" \
  | jq '{models,compression_totals}'
```

The response keys each row by the requested model and reports `local_completions`, `cloud_completions`, `saved_micros`, and `cloud_spent_micros`, alongside the context-compression value rows. See [model-host.md](model-host.md) ("Value delivered") for the full response shape and durability notes.

Without a running proxy, `sbproxy ai ledger report` renders the same report from the ledger file directly:

```bash
sbproxy ai ledger report /var/lib/sbproxy/models/value-ledger.redb
```

The command reads the redb database offline. When a `serve:` block sets `cache_dir`, the durable ledger lives at `<cache_dir>/value-ledger.redb`; point the command at that file. While a proxy is serving, the Admin endpoint above is the live view of the same data.

Text mode (the default) prints one row per model with local and cloud completion counts and the saved and spent totals rendered as decimal dollars, followed by the per-model compression rows and their token and gross avoided-cost totals. `--format json` emits the exact object the Admin endpoint serves, raw micros and all, so scripts can consume either surface interchangeably.

A missing or empty ledger file is a normal state, not an error: the command reports that no value has been recorded yet and exits 0. The report never invents a number in either mode. A model without a `reference:` price never appears in the lane split, and a compression target with no known input price keeps its `tokens_saved` while claiming zero avoided dollars.

The related `sbproxy ai ledger verify <path>` command verifies the hash-chained AI usage ledger described in [ai-usage-ledger.md](ai-usage-ledger.md), which is a separate artifact from the Value Ledger.

By explicitly isolating the "local" and "cloud" lanes within the ledger, SBproxy provides an accurate, verifiable account of the real-world savings generated by your self-hosted AI investments.
