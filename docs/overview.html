One proxy for the five kinds of AI traffic

SBproxy is a reverse proxy for the boundary where AI traffic enters and leaves your infrastructure. Five kinds of traffic cross that boundary now, and each one arrived with its own half-finished tooling. We built one data plane that treats all five as things to route, govern, meter, and prove.

APIsThe traffic you already had, now called by agents that retry harder than any browser.
MCP serversTool catalogs your agents call. Federated, governed, versioned, composed.
ModelsLLM providers and local weights, behind one endpoint with budgets and guardrails.
AgentsA2A peers and bot callers, identified by cryptographic trust tiers rather than user-agent strings.
CrawlersAI scrapers reading your content. Detected, priced, and either served or refused on your terms.

The reason to put one proxy there instead of five products is not consolidation for its own sake. It is that the interesting policy questions now span the classes. The API request arrives from an agent. The agent got its tools from an MCP server. The tool call fans out to a model. Whether any of that was allowed, and what it cost, and who to bill, is one question with one audit trail, and you cannot answer it from four dashboards.

We are honest about what this is not. LiteLLM knows more model providers than we do. Varnish will out-cache us on exotic invalidation. Kong has a plugin bazaar a decade deep. If you need maximum breadth in any single class, buy the specialist. SBproxy is for the boundary itself: every class crosses it through the same pipeline, the same policy engine, and the same evidence stream.

The request path

Every request, whatever its class, walks the same pipeline. Policies and transforms attach per origin, so a hostname serving an OpenAI-compatible endpoint and a hostname proxying a legacy REST API run different policy chains through identical machinery.

The last box is the one we would defend in an argument. Most gateways log requests. SBproxy emits a decision record for each governance decision, sequence-numbered so a gap is detectable, redacted so positions of sensitive matches are recorded without the matched text, and shaped for a SIEM rather than for our own dashboard. When an auditor asks why an agent's tool call was allowed on March 3rd, "we have Grafana" is not an answer. A signed, gapless decision trail is. The full field contract is in decision-records.md.

APIs

The API half of SBproxy is a working reverse proxy: routing by hostname, load balancing with five strategies, health checks, circuit breaking, response caching with four backends, compression, CORS, redirects, and a transform layer that can reshape requests and responses in CEL, Lua, JavaScript, or WASM. If you have used any modern proxy, this part will feel familiar, and that is deliberate.

Where we diverge from the field is enforcement posture. Every API security vendor publishes a mapping document explaining how you could configure their product against the OWASP API Security Top 10. We got tired of reading those, so type: owasp_api_top10 is a policy you enable by name. The compiler expands it into concrete policy entries, backs off wherever you already wrote an overlapping policy by hand, and then tells you the truth in a five-state manifest: which items are enforced, which are report-only, which need one operator decision it refuses to guess (rate budgets behind an undeclared load balancer, for one), and which three of the ten no proxy can honestly claim. sbproxy plan and GET /admin/owasp-api-pack both show the manifest, so "enable: all" can never silently mean "enabled: some."

Alongside the pack: object-level authorization with enumeration detection (a caller sweeping /orders/1 through /orders/500 trips a tenant-scoped, constant-work detector), a DLP policy that scans URI, headers, and request bodies with match positions in the audit trail, and request validation against your OpenAPI spec. Start with api-security.md, or the owasp-api-top10 and object-authz examples.

What we concede: we are not a CDN and do not want to be. No edge PoPs, no image optimization, no per-plugin marketplace. Front us with one if you need one.

MCP servers

MCP is where the market is strangest right now. Composition products (StackOne, superglue, the Arazzo spec) can merge several API calls into one tool, but the steps run inside code the gateway never sees. Governance products can approve and deny tools, but compose nothing. Nobody was shipping both, which struck us as odd, because the whole point of putting an MCP gateway in front of agents is that every step should be governed.

So SBproxy's MCP action does both jobs through one catalog. Federation turns upstream MCP servers and OpenAPI specs into a governed tool list: RBAC by principal, argument policies in CEL or Rego, quotas, session-flow enforcement, content filters on results, tool versioning with lockfile digests so an upstream cannot swap a tool's contract under your agents, and draft or deprecated status per server. Composition (federated_servers[].type: local) lets you declare a tool entirely in config: a fixed value, a single HTTP call, or a dependency-ordered DAG of calls with CEL step conditions, per-step retry, and a response shaped by a template, JavaScript, or Lua. Because composed tools publish into the same catalog, every governance gate applies to them with no extra wiring, per step, egress-gated, fail-closed.

You can also point an MCP client at the proxy's own admin surface and operate it conversationally; that is the admin-mcp example. For composition, read mcp-compose.md and run mcp-compose or its JavaScript twin mcp-compose-js. The governance model is in mcp.md and mcp-security-coverage.md.

What we concede: stdio-only MCP servers are proxied through a supervised bridge rather than natively, and the composition engine runs steps sequentially in this release. Both are stated in the docs rather than discovered in production.

Models

The model gateway (action: ai_proxy) presents one OpenAI-compatible endpoint and routes behind it: multiple providers, weighted groups, cascade and race strategies, cost-optimized and outcome-aware routing, and local serving through llama.cpp hosts the proxy itself supervises as a cluster. Budgets meter tokens and dollars per key, per tenant, and per agent, with hard cutoffs. Guardrails screen prompts and outputs for PII, secrets, and injection, and when one blocks, the decision record carries bounded match positions so you can see what tripped without the log itself becoming the leak.

LiteLLM is the honest comparison here, and if your problem is "call any of ninety providers from Python," it is the right tool. Our bet is that the provider list matters less than what wraps it: a gateway that treats a model call like any other governed boundary crossing, with the same policy engine, evidence trail, and settlement machinery as the rest of your traffic. Virtual keys with per-key policy, spend that reconciles into a usage ledger, and guardrail decisions that land in the same SIEM feed as your WAF blocks.

Start at ai-gateway.md, then the ai-gateway-quickstart, ai-multi-provider, and ai-local-serving examples.

Agents

Agent-to-agent traffic is the newest class and the one with the least settled tooling anywhere. SBproxy's position: an agent is a caller whose identity should be established cryptographically, not inferred from a user-agent string. The trust-tier model classifies every caller into one of four tiers, where the signed tier is earned only through verifiable mechanisms (CAP tokens, Web Bot Auth signatures, known-agent verification), and policy can key on the tier. The A2A action proxies agent-card exchanges and rewrites the card so your internal topology never leaks, serves the well-known card path, and applies prompt-injection screening to agent payloads.

There is no incumbent to compare against here; API gateways treat agent traffic as generic HTTP, and the agent frameworks assume you trust your peer. We think the boundary deserves the same skepticism it gives everything else. See a2a-gateway.md and the a2a-protocol example.

Crawlers

AI crawlers are the class most sites handle with a blunt instrument: block them all or let them all in. SBproxy detects them (headless-browser TLS fingerprinting, reverse-DNS agent verification, declared-agent signatures), reads and serves content preferences, and then gives you a third option beyond allow and deny: price it. Crawl control can serve different tiers to different agents, meter what they read, and settle through x402 payment challenges, so a scraper that wants your content at scale pays for it instead of being an abuse problem.

Cloudflare will block crawlers at the edge, and robots.txt will ask them nicely. Charging them requires the detection, the metering, and the settlement to sit in one data plane, which is the case we built. See ai-crawl-control.md, content-for-agents.md, and the ai-crawl-tiered example.

Where to start

curl -fsSL https://download.sbproxy.dev | sh
sbproxy validate sb.yml
sbproxy sb.yml

Homebrew (brew install soapbucket/tap/sbproxy) and Docker images are also published per release. The getting-started guides (one per estate: APIs, AI, agent identity) get a proxy answering in a few minutes; the roughly two hundred runnable examples under examples/ are the fastest way to see any single feature demonstrated against a live binary, each with a recorded terminal session showing real output.
