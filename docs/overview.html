One proxy for the five kinds of AI traffic

SBproxy is a reverse proxy for the boundary where AI traffic enters and leaves your infrastructure. Five kinds of traffic cross that boundary now, and each one arrived with its own half-finished tooling. We built one data plane that treats all five as things to route, govern, meter, and prove.

APIsThe traffic you already had, now called by agents that retry harder than any browser.
MCP serversTool catalogs your agents call. Federated, governed, versioned, composed.
ModelsLLM providers and local weights, behind one endpoint with budgets and guardrails.
AgentsA2A peers and bot callers, identified by cryptographic trust tiers rather than user-agent strings.
CrawlersAI scrapers reading your content. Detected, priced, and either served or refused on your terms.

The reason to put one proxy there instead of five products is not consolidation for its own sake. It is that the interesting policy questions now span the classes. The API request arrives from an agent. The agent got its tools from an MCP server. The tool call fans out to a model. Whether any of that was allowed, and what it cost, and who to bill, is one question with one audit trail, and you cannot answer it from four dashboards.

We are honest about what this is not. LiteLLM knows more model providers than we do. Varnish will out-cache us on exotic invalidation. Kong has a plugin bazaar a decade deep. If you need maximum breadth in any single class, buy the specialist. SBproxy is for the boundary itself: every class crosses it through the same pipeline, the same policy engine, and the same evidence stream.

The request path

Every request, whatever its class, walks the same pipeline. Policies and transforms attach per origin, so a hostname serving an OpenAI-compatible endpoint and a hostname proxying a legacy REST API run different policy chains through identical machinery.

The last box is the one we would defend in an argument. Most gateways log requests. SBproxy emits a decision record for each governance decision, sequence-numbered so a gap is detectable, redacted so positions of sensitive matches are recorded without the matched text, and shaped for a SIEM rather than for our own dashboard. When an auditor asks why an agent's tool call was allowed on March 3rd, "we have Grafana" is not an answer. A signed, gapless decision trail is. The full field contract is in decision-records.md.

APIs

The API half of SBproxy is a working reverse proxy, and most of a config reads like one: origins keyed by hostname, forward rules with CEL predicates picking actions per path, retries with backoff, DNS-based service discovery, and header rewriting in both directions. If you have used any modern proxy, this part will feel familiar, and that is deliberate.

Routing and resilience

The load_balancer action spreads traffic with eight algorithms (round-robin, weighted random, least connections, IP, URI, header, and cookie hash, and ketama-style ring hash) plus five named custom strategies, including GPU-aware and LoRA-aware placement for model backends and a bandit strategy that learns from outcomes. Health is three layers deep: active probes, passive outlier ejection, and per-target circuit breakers, with blue-green and canary modes, backup targets, and priority tiers on top. Response caching runs on four backends (memory, file, memcached, Redis) with optional AES-256-GCM encryption at rest and a cache-reserve tier. routing.md and routing-strategies.md cover it; routing-strategies and cache-reserve run it.

Security posture

Where we diverge from the field is enforcement honesty. Every API security vendor publishes a mapping document explaining how you could configure their product against the OWASP API Security Top 10. We got tired of reading those, so type: owasp_api_top10 is a policy you enable by name. The compiler expands it into concrete policy entries, backs off wherever you already wrote an overlapping policy by hand, and then tells you the truth in a five-state manifest: which items are enforced, which are report-only, which need one operator decision it refuses to guess (rate budgets behind an undeclared load balancer, for one), and which three of the ten no proxy can honestly claim. sbproxy plan and GET /admin/owasp-api-pack both show the manifest, so "enable: all" can never silently mean "enabled: some."

The rest of the API security surface, each usable alone or via the pack:

  • Object authorization (object_authz): BOLA and BFLA enforcement from declared ownership rules, plus enumeration detection. A caller sweeping /orders/1 through /orders/500 trips a tenant-scoped, constant-work detector even with no rules configured, audit-only until you declare ownership. object-authz.md
  • DLP: pattern scanning across URI, headers, and request bodies (16 KiB cap, on by default), with match positions in the audit trail and never the matched text. api-security.md
  • WAF with custom rules in Lua or JavaScript, persistent blocks keyed by CEL expressions, and exposed-credential checks.
  • Validation: request shape rules, OpenAPI-spec validation against your published contract, HTTP framing hardening (dual content-length and TE refusals), CSRF, SRI, content digests, and security headers.

What we concede: we are not a CDN and do not want to be. No edge PoPs, no image optimization, no per-plugin marketplace. Front us with one if you need one.

MCP servers

MCP is where the market is strangest right now. Composition products (StackOne, superglue, the Arazzo spec) can merge several API calls into one tool, but the steps run inside code the gateway never sees. Governance products can approve and deny tools, but compose nothing. Nobody was shipping both, which struck us as odd, because the whole point of putting an MCP gateway in front of agents is that every step should be governed.

Federation, governed

The mcp action federates three kinds of tool sources behind one endpoint: real upstream MCP servers, OpenAPI specs converted one-operation-per-tool, and local tools declared entirely in config. All three publish into one catalog, and the governance gates key on the catalog, so they apply identically regardless of where a tool came from:

GateWhat it decides
RBACWhich principals see and may call which tools; default deny, per-tenant labels.
Approval statusA draft server's tools are invisible and refused everywhere, including the served TypeScript code-mode module; deprecated warns.
Tool versioningLockfile digests pin each tool's contract. An upstream that swaps a tool's schema under your agents trips the version gate instead of silently changing behavior.
Argument and result policiesCEL or Rego over call arguments and results, per tool.
Quotas and flowCall budgets per principal, and session-flow taint rules (a tool that read untrusted content can be barred from calling outbound tools afterward).
Content filtersSecret and PII screening on arguments and results, with warn, redact, and block modes.
EvidenceA decision record per governance decision, gapless sequence numbers per session.

Composition

Composition (federated_servers[].type: local) lets you declare a tool in config: a fixed value, a single HTTP call, or a dependency-ordered DAG of calls under steps:, wired together with ${args.x} and ${steps.name.body.x} interpolation that fails closed on any missing path. Steps carry CEL conditions, per-step retry, and continue_on_error; the whole call runs under a budget (30 seconds default, five minutes cap); every outbound dial goes through the server's mandatory deny-by-default egress allowlist; and the final response is shaped by a template, JavaScript, or Lua, in the same sandboxes with the same watchdogs the rest of the proxy uses. Because composed tools publish into the same catalog, every gate in the table above applies to them per step, with no extra wiring.

Two more MCP surfaces worth knowing: the proxy's own admin API is exposable as an MCP server, so you can operate the gateway conversationally from any MCP client (admin-mcp, admin-mcp.md), and agents that prefer writing code to calling tools can fetch a generated TypeScript module of the catalog (cloudflare-code-mode.md). Read mcp.md for federation, mcp-compose.md for composition, and mcp-security-coverage.md for the threat-by-threat coverage table. Runnable: mcp-compose, mcp-compose-js, mcp-local-tools.

What we concede: stdio-only MCP servers are proxied through a supervised bridge rather than natively, and the composition engine runs steps sequentially in this release. Both are stated in the docs rather than discovered in production.

Models

The model gateway (action: ai_proxy) presents one OpenAI-compatible endpoint and routes behind it across a 72-provider catalog, from the hosted majors through Bedrock and OpenRouter down to llama.cpp hosts the proxy itself supervises as a local cluster with GPU-aware placement. Model aliases decouple the name your clients send from what serves it, so swapping providers is a config edit rather than a client rollout.

Routing that reads the traffic

Routing strategies go well past round-robin: cascade (try cheap, fall through to strong on refusal or low confidence), race (first useful answer wins), cost-optimized, outcome-aware (routes on measured quality of prior answers), classifier-driven (an ONNX classifier picks the lane), and LLM-aware resilience that understands provider-specific failure modes rather than treating every 429 alike. Shadow routing mirrors traffic to a candidate model without serving its answers, for evaluation before cutover. ai-gateway.md is the reference; ai-cascade-routing, ai-race, and ai-shadow run the shapes.

Spend, safety, and context

  • Budgets and keys: virtual keys with per-key policy and attribution, token and dollar budgets per key, tenant, and agent, hard cutoffs, predictive budget alerts, and a reconcilable usage ledger with Stripe meter export. (ai-virtual-keys, ai-usage-ledger.md)
  • Guardrails: PII, secrets, and prompt-injection screening on input and output, streaming-aware, with external guardrail services and a mesh mode that fuses verdicts. When a guardrail blocks, the decision record carries bounded match positions so you can see what tripped without the log becoming the leak. (ai-guardrails)
  • Context engineering: semantic caching keyed on deterministic request features, context compression backed by Redis or mesh peers, RAG wiring for local retrieval, and hosted prompt templates. (ai-context-compression.md)

LiteLLM is the honest comparison here, and if your problem is "call any of ninety providers from Python," it is the right tool. Our bet is that the provider list matters less than what wraps it: a gateway that treats a model call like any other governed boundary crossing, with the same policy engine, evidence trail, and settlement machinery as the rest of your traffic.

Agents

Agent-to-agent traffic is the newest class and the one with the least settled tooling anywhere. SBproxy's position: an agent is a caller whose identity should be established cryptographically, not inferred from a user-agent string.

The trust-tier model classifies every caller into one of four ordered tiers, and the signed tier is earned only through verifiable mechanisms: CAP tokens (capability tokens with verdict-mapped responses, 401 with a license challenge, 403 by refusal code, 429 with rate headers), Web Bot Auth HTTP-signature verification, or known-agent verification by reverse DNS. Policy can key on the tier, so "browsers get the site, unsigned bots get a challenge, signed agents get the API" is three config lines rather than a WAF science project. trust-tiers.md and cap.md are the references.

The a2a action proxies agent-to-agent JSON-RPC with the skepticism the protocol deserves: envelope trust rules, delegation-depth caps, cycle detection, caller and callee allowlists, prompt-injection screening on agent payloads (a2a-prompt-injection), and agent-card handling that serves the well-known card path and rewrites the card so your internal topology never leaks. Agent skills give a declared agent a scoped capability set, and agent budgets meter what an agent may spend across every origin it touches (agent-skills.md, agent-budget.md).

There is no incumbent to compare against here; API gateways treat agent traffic as generic HTTP, and the agent frameworks assume you trust your peer. We think the boundary deserves the same skepticism it gives everything else. See a2a-gateway.md and the a2a-protocol example.

Crawlers

AI crawlers are the class most sites handle with a blunt instrument: block them all or let them all in. SBproxy detects them with mechanisms that do not trust the user-agent string (headless-browser TLS fingerprinting, reverse-DNS agent verification, declared-agent signatures), reads and serves content preferences (content-for-agents.md), and then gives you a third option beyond allow and deny: price it.

Crawl control serves different content tiers to different agents, meters what each one reads, and settles through x402 payment challenges, so a scraper that wants your content at scale pays for it instead of being an abuse problem. The tiered example (ai-crawl-tiered) shows a free tier, a metered tier, and a refusal tier running side by side on one origin. Cloudflare will block crawlers at the edge, and robots.txt will ask them nicely; charging them requires the detection, the metering, and the settlement to sit in one data plane, which is the case we built. ai-crawl-control.md is the reference.

Beyond inline scripts, an extension bundle packages logic as a versioned directory (JavaScript, TypeScript, or compiled WASM) loaded from disk or a digest-pinned git source: auth, policy, action, and transform hooks in the core pipeline, plus AI guardrail, tool-call, and routing hooks, and payment lifecycle hooks. scripting.md carries the per-site contracts; plugins.md and extension-bundles.md map the rest.

Evidence

Four surfaces, one principle: the record of what the proxy decided should be usable by someone who does not run the proxy.

  • Decision-audit records: one per governance decision, gapless sequence numbers, a versioned field contract (decision-records.md), match positions instead of matched text, and honest disposition (a detect-only hit never claims the 403 it did not return).
  • Structured events: thirteen event kinds on an internal bus with SIEM egress (events.md), covering everything from guardrail triggers to refused egress dials.
  • Metrics: Prometheus families under a published stability contract (metrics-stability.md), so a dashboard you build today does not break on upgrade; Grafana dashboards and alert rules ship in the repo.
  • Access log and OTLP: structured JSON access logs with custom fields in CEL, Lua, or JavaScript, and OpenTelemetry export for traces, metrics, and logs. The OTLP exporters themselves pass through the proxy's egress gate and are re-verified on reload, because telemetry that can leak the prompts it audits is a finding, not a feature. (observability.md)

Operating it

One YAML file drives everything, and the tooling around that file is where day-two actually lives:

  • Validation that names the knob: sbproxy validate refuses bad configs with the field path and the fix, and a knob that cannot work in this release is refused at load rather than accepted and ignored. Dead switches are how outages hide.
  • Plan before apply: sbproxy plan previews what a config will enforce, including the OWASP pack manifest, before traffic sees it.
  • Config history: a durable, content-addressed ring of every applied config, browsable from the CLI (sbproxy config history, config show), the admin API, and the console, with secrets masked in every displayed view. (configuration.md)
  • Admin surface three ways: a JSON API (admin-api-reference.md), an embedded web console (admin-ui.md), and the same API served as MCP tools for conversational operations.
  • Hot reload for nearly everything, with the config authority model for fleets: a subscriber applies signed config bundles and refuses a bundle whose references do not resolve. (config-authority-drills.md)
  • Kubernetes: a native operator with CRDs and a reconcile loop, alongside plain Docker and systemd deployment. (operator-runbook.md)

Metering and settlement

Billing machine callers is a proxy concern now, whether the caller is a crawler reading your content or an agent spending tokens. SBproxy meters usage per key, tenant, and agent, keeps a reconcilable ledger (SQLite, with durable payment nonces so a settled request is served exactly once and a replay is refused), issues x402 payment challenges, and exports usage to Stripe meters. The 402-challenge.md walkthrough drives a payment end to end; ai-usage-ledger shows the reconciliation report an operator actually reads.

Where to start

sbproxy sb.yml

Homebrew (brew install soapbucket/tap/sbproxy) and Docker images are also published per release. The getting-started guides (one per estate: APIs, AI, agent identity) get a proxy answering in a few minutes; the roughly two hundred runnable examples under examples/ are the fastest way to see any single feature demonstrated against a live binary, each with a recorded terminal session showing real output.
